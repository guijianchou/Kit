# WinGet plugin

Winget is a Kit module for checking installed applications against the official WinGet community repository. It uses Microsoft's Windows Package Manager COM API for structured package identity, versions, installer metadata and release notes, and the installed WinGet CLI for explicit installation and updates. The installed App Installer/WinGet supplies the package manager; Kit does not install a separate copy.

## Use

1. Enable **WinGet** in Kit. The independent `Kit.WingetService.exe` detects the local WinGet installation.
2. **Software Updates** lists installed and new versions. Reload manually or enable daily checks. Filter by source/name/ID, choose exact matches, and opt into Unknown installed versions when needed. Ignored software is hidden from normal update lists and notifications until restored in **Manage ignored updates**.
3. **Discover Packages** searches the WinGet community catalog. Enter at least two characters and press Enter or Search; broad queries are capped at 100 results. Names and IDs appear first. Version and installed-state columns explicitly remain unresolved until you open details or prepare the selected packages; an empty version is not evidence that a package is uninstalled. Already installed results remain visible but cannot be installed again through discovery.
4. **Installed Packages** lists software known to Windows Package Manager, including matched WinGet packages and unmatched Local PC / MSIX records. The MSIX label includes Store and sideloaded applications; it does not claim every MSIX came from the Store. Refresh loads the inventory. Select uniquely identified software to uninstall through native WinGet.
5. Check up to 50 visible rows, choose installer options if needed, then use **Update / Install / Uninstall selection**. Kit prepares all versions and agreements for one explicit confirmation, then processes the queue sequentially. Detailed, compact and grid views share selection; changing filters clears hidden selections. Focusing a row for details does not select it for a batch operation.
6. Use **Export to CSV** for the visible list or **Export selected bundle** for a standard WinGet JSON package list. Bundles support WinGet-source software; local-only installed records cannot become catalog imports. CSV metadata is quoted and protected against spreadsheet formula interpretation.

Workspace tabs are ordered Updates, Installed and Discover. Each workspace remembers its own filters, selected sources, sorting and view for the lifetime of the cached page. Repeating a catalog search retains the previous query and results until the replacement succeeds; failed or cancelled searches keep the previous result set. Resolving a discovery row updates that row in place, retaining focus and checked selection. Package details open immediately with loading, cancellation and retry feedback, and expose the publisher's homepage, license and release links when available.

The page uses Kit's WinUI 3 + Mica shell and a UniGetUI-inspired workspace: the module switch comes first, automatic settings fold away, filters sit beside the table (in a flyout on narrow windows), command overflow adapts to width, and details appear in a dialog. The content is constrained to the actual viewport. Only changed status values are published to the page; polling does not reset templates, row identity, focus or selection. Operation summaries remain visible after completion, with direct access to history and expandable output. No UniGetUI code or dependency is included.

WinGet downloads, verifies and runs the exact selected version, including required dependencies. Native installer/uninstaller windows and administrator/UAC prompts appear normally. The hidden WinGet CLI output is normalized into a bounded tail (up to 16,384 UTF-16 code units): terminal control sequences are removed and carriage-return progress redraws replace the current line. Output updates are throttled to 250 ms; the Settings page polls once per second while visible. Output text is informational and is never parsed to infer localized progress percentages or success. Options support silent mode, user/machine scope, installation architecture and explicit unknown-version upgrades. Kit does not elevate its service on demand, bypass hash checks, force an installation or schedule automatic installs.

Package agreements are shown before an explicit installation and accepted only by that confirmation. Unsupported installers retain an advanced manual command. Save work in the target application before updating it.

## Scope and storage

- Search and updates use the official `winget` community source. Installed inventory includes Local PC and MSIX records; Microsoft Store catalog search and custom package managers are outside this module. A failed query is shown as an error, not an empty success.
- Unknown installed versions are hidden by default and omitted from notifications; opt in to show/upgrade them. Pins, source policy and installer applicability remain governed by Windows Package Manager.
- Configuration: `%LOCALAPPDATA%\Kit\Winget\settings.json`, owned by Kit's settings/native module contract. `daily_check_enabled` and `notify_updates` default to true; the plugin itself defaults to off.
- Service state and scheduling watermarks: `%LOCALAPPDATA%\Kit\Winget\State`. Successful update-check results survive Settings navigation and service restart. Failed checks back off rather than looping every minute. Ignored identities, the latest bounded queue (50 items) and recent operation history (100 items) also persist here. Each persisted result retains at most 4 KiB of UTF-8 output with a truncation marker; the state file remains capped at 4 MiB and older output can be omitted with an explicit marker while preserving package identities, errors and recovery state. Search results and installed inventory are refreshed in memory.
- Logs: `%LOCALAPPDATA%\Kit\Winget`, under module/service log subdirectories. Logs do not fall back to LocalLow.
- Legacy download-export cache (no separate UI action): `%TEMP%\Kit\Winget\<operation-guid>`. On a new/completed download, Kit removes its marked operation directories older than 7 days, then the oldest completed directories until the retained cache is at most 4 GiB. An individual export over 4 GiB is rejected after downloading; WinGet does not expose a pre-download size limit. Active downloads are kept during cleanup. Foreign directories and reparse points are never traversed or deleted.
- Installation cache: native `winget install` / `upgrade` own their temporary download and hash-verification workflow. These commands do not support `--download-directory`; Kit does not misuse `--location`, which changes the installation destination.
- Windows notifications report newly discovered update sets. Delivery depends on Windows notification settings; no installation is scheduled by a notification.

## Architecture

`WingetModuleInterface` implements `KitModuleIface`/`kit_create`, launches its service asynchronously with the Runner's current token, and stops it through a module-specific event. It does not request elevation. If Kit already runs as administrator, the service inherits that token; otherwise WinGet requests administrator permission only when the installer needs it. `WingetService` owns operations and scheduling. Settings sends short commands over the existing current-user Kit service pipe, then polls status while the cached page is visible. Long operations do not run on the UI thread. The UI uses Kit's WinUI 3 + Mica shell and bilingual resources.

`WingetLib` contains the COM adapter, immutable models, shared JSON contract, installer applicability rules, native CLI invocation and legacy temporary download management. The Microsoft COM interop package is used to generate the WinRT projection; the installed Windows Package Manager executes operations. Module and service icons are derived from the user-provided `winget.png` artwork in [Assets](Assets/README.md). `tools/Generate-WingetAssets.py` regenerates Settings images and the ten-size native/service ICO.

Discovery reads only catalog identities and names. `DefaultInstallVersion` and even available-version enumeration can fetch per-package version data on a cold WinGet cache, so they must not run across the complete search result list. Search waits are bounded to 30 seconds. If a native COM request has not actually finished, its worker retains the single client operation slot after cancellation or timeout; retries cannot accumulate abandoned workers. A selected detail request resolves the current package version and installed state, and preparation validates the complete identity, installer options, permissions and agreements before it can produce an installation confirmation. Search stage/elapsed diagnostics use Kit's existing log level; disabling logging remains respected.

The runtime must retain `Microsoft.Management.Deployment.dll` (the 227,872-byte x64 static activation factory from ComInterop 1.10.340), `Microsoft.Management.Deployment.winmd`, and `Winget.ComInterop.NOTICE.txt` alongside both the service and Settings executable. These files flow through the `WingetLib` project reference. The native factory enables unpackaged COM activation and marshaling; copying only `Kit.WingetLib.dll` is insufficient. The generated projection uses Kit's existing `WinRT.Runtime` 2.2.0.48161. The factory and metadata do not contain or replace the installed WinGet engine.

Read-only COM operations accept cancellation. Cancelling a queue removes its not-yet-started items and keeps the current native operation occupied until the real CLI exit. Cancel an already running installer in its native window. Kit does not kill a running installer or claim to roll it back. Successful WinGet exits remain successful if installed-version registration is delayed; Kit reports pending verification and performs a later read-only check. Disabling the module or exiting Kit requests cancellation, waits up to 5 seconds, and may then terminate the service host. An installer already started by WinGet can continue independently. Before installation, the service persists a pending operation marker; after an interrupted operation, startup performs a read-only update check even when daily checking is disabled. Cached package actions stay unavailable until that check succeeds. Recovery never retries installation automatically. On restart, running queue entries become NeedsVerification and waiting entries become Cancelled. Preparation tokens expire after ten minutes and are consumed once; a changed package/version/options snapshot requires a fresh confirmation. Ordinary package failure can continue only after a successful read-only state check; UAC cancellation or unverifiable state stops remaining items.

Update checks inspect WinGet's installing catalog before and after querying available updates. An active WinGet CLI process (including external search/show commands), active installation or unverifiable installation state defers checks and installation, preserving any recovery marker. These observers never cancel another installation. Package identity, source and exact selected version are re-resolved before operations, and permission eligibility is rechecked immediately before installation. Downloads retain hash checking; native installation never adds hash-bypass, force, dependency-skip or automatic-reboot flags. Fresh installation uses `--no-upgrade`; updates use the dedicated `upgrade` command.
